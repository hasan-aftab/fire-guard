# WhatsApp reminders

Fire Tracker sends operational inspection and certificate reminders through Meta WhatsApp Cloud API. The admin **WhatsApp** page manages sending numbers, WABA template mappings, test sends, and delivery history. No access token or Meta app secret is sent to the browser.

## Production setup

1. Keep `APP_KEY` stable and backed up securely. Account access tokens use Laravel's encrypted cast; losing or regenerating this key makes stored tokens unreadable. Restore the original key or replace each account token after a rotation.
2. Set `WHATSAPP_APP_SECRET` to the Meta app secret and `WHATSAPP_WEBHOOK_VERIFY_TOKEN` to a separate strong random string. Keep both in the deployment secret store. `WHATSAPP_GRAPH_VERSION` defaults to `v25.0` to match the tested integration configuration and can be changed centrally after checking Meta's current supported version. No sender credential belongs in `.env.example`.
3. In Meta Business settings, create a System User (Settings → Users → System Users), grant it access to the WhatsApp Business Account, then generate a token for this app with `whatsapp_business_messaging` for sending and `whatsapp_business_management` for phone and template reads. Set the token expiry to **Never** — only System User tokens support that; user tokens and the Getting Started token expire in hours or days and come back as error 190. A temporary Getting Started token is for testing, not unattended production use.
4. In the admin page, add each sending phone number with its visible number, Meta Phone Number ID, WABA ID, and scoped token. Multiple numbers may share one WABA. Verify each connection. Verification lists phone numbers from the declared WABA and checks the ID and normalized display number. Select one verified, active, production number as default for automatic reminders. Test accounts may send explicit tests but cannot become the automatic default.
5. Create and submit inspection and certificate templates in Meta WhatsApp Manager. Use the current Meta category guidelines for their factual operational content. Map each purpose to the approved template name and language in Fire Tracker, then sync from Meta. Mappings are per WABA, so all numbers on one WABA share them. The integration supports numbered **BODY text parameters** only; set the parameter order to match `{{1}}`, `{{2}}`, etc. Available facts are `client_name`, `site_name`, `subject_name`, `due_date`, and `timing`. Dynamic headers and buttons need a later payload design and are rejected by sync. A mapping sends only when enabled, Meta reports `APPROVED`, and the parameter check succeeds.
6. Expose `GET` and `POST /webhooks/whatsapp` over HTTPS. Enter the URL and the verify token in Meta's Webhooks product, subscribe to the `messages` field, and subscribe the app to each WABA. One WABA subscription covers its phone numbers. The GET route returns `hub.challenge` only for the configured token. The POST route verifies `X-Hub-Signature-256` using the raw body and app secret before queueing status events.
7. For each client, enter a canonical international WhatsApp phone number and turn on **Send WhatsApp reminders** only after recording the client's agreement to operational reminders. This Boolean is the application's eligibility flag; it does not itself prove Meta opt-in. Keep consent evidence in your operational records. The general client `phone` field remains independent.
8. Run the existing daily scheduler and a queue worker. The scheduler discovers both email and WhatsApp deliveries from the same asset `next_service_due` and certificate `expiry_date` rules. The database queue must be running for automatic sends and webhook status jobs.

## Delivery and incident handling

- The shared `reminder_deliveries` identity includes the channel, reminder type, record, due date, offset, and recipient. WhatsApp-specific `whatsapp_messages` records keep sender, WABA, template, Meta `wamid`, attempts, timestamps, and safe errors. Deactivation does not delete history.
- A successful `/messages` response with a `wamid` means **submitted**. Only signed Meta status webhooks advance to `sent`, `delivered`, or `read`, or report `failed`. Delayed and duplicate webhooks cannot lower a delivered/read state. Incoming customer messages are ignored because this integration has no inbox.
- Message POSTs have connection and request timeouts and **no automatic HTTP retry**. A connection timeout or worker interruption after claiming a message is `uncertain`: Meta may have accepted it. Review Meta activity before any human action. The UI offers one controlled retry only for a definite HTTP rejection with no `wamid`; it never retries an uncertain or webhook-failed message automatically. Rate limit errors are recorded as rejections for review, with no blind resend.
- The dashboard excludes flagged test messages from operational KPIs. Delivery rate is `(delivered + read) / (sent + delivered + read + failed)` for the selected period. Submitted messages awaiting a status are outside that denominator. Dates, filters, counts, and pagination are computed by the server.
- The test-number option accepts a libphonenumber **possible** international sender because Meta's reserved test numbers may not pass normal validity metadata. It still requires live Meta ownership verification. Production senders and all customer recipients require libphonenumber-valid E.164 values.

## Local development and migrations

Automated tests use `Http::fake()` and SQLite `:memory:`. They need no Meta token. For a manual test, add a Meta test account through the admin page, verify it, map a Meta-approved test template, and send **one** test message to a recipient that Meta permits. This requires a reachable HTTPS webhook URL to observe delivery statuses. Never use a customer recipient for an integration test.

The new WhatsApp tables have create-only migrations. The client WhatsApp columns live in the original `create_clients_table` migration per this repository's migration convention. Existing local MySQL databases do not gain those columns by running only new migrations; inspect the data and migration history before refreshing a disposable demo database. Do not reset a database that contains report history to keep.

Meta references checked for this integration: [official WhatsApp Cloud API Postman collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api), [official message-status webhook examples](https://www.postman.com/meta/whatsapp-business-platform/request/rgtfq23/message-status-update-notifications), and [Meta's archived Cloud API SDK webhook verification reference](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/). Recheck Meta's live template category, pricing, and version documentation before production onboarding; the direct developer documentation was rate-limited during implementation. No pricing rates are stored here.
