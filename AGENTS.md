# Fire Tracker PNG

Fire-safety compliance tracker for PNG businesses. Inertia v3 + React SPA, SQLite,
no API layer, no queue workers for domain logic.

> **Read this first:** this file is **hand-written only** and is tracked in git.
> Laravel Boost writes its generated guidelines to `.boost-guidelines.md`, which is
> gitignored, at the path set in `config/boost.php`. `php artisan boost:update` (wired
> to `composer post-update-cmd`) rewrites that file in place and never touches this
> one. Run `php artisan boost:install` on a fresh clone to recreate it.
>
> Note that Boost redirects **both** of its enabled agents here, not just opencode:
> `claude_code` defaults to `AGENTS.md` rather than `CLAUDE.md`, so a
> partial override silently re-append the block to this file.
>
> There is no `README` and no `.ai/rules` directory. `/CLAUDE.md`, `/boost.json`,
> `/opencode.json`, `/.mcp.json`, `.agents/` and `.claude/` are gitignored and
> regenerated by `boost:install`.

## Commands

Verified working. Run order matters — `composer ci:check` is exactly what CI runs.

```bash
composer run dev            # server + queue:listen + pail + vite, together
php artisan dev:list        # what the above actually runs

# focused verification (fast, <5s each)
php artisan test tests/Feature/AssetControllerTest.php --compact

composer types:check        # phpstan level 7

# full gate — same order as .github/workflows/tests.yml
composer ci:check           # npm run check → npm run types:check → full test suite
```

Non-obvious details:

- `npm run check` is `vp check` = **format check + lint** with `denyWarnings: true` and
  `typeAware: true`. Warnings fail it. `npm run check:fix` fixes. Its config lives in
  `vite.config.ts` (`lint` / `fmt` blocks) — printWidth 80, tabWidth 4, single quotes,
  and **Tailwind class sorting is enforced**.
- `composer lint` _fixes_ (`pint --parallel`); `composer lint:check` only tests. Run the
  fixer, never the test variant, before finalizing PHP edits.
- `composer test` = config:clear + pint --test + phpstan + test. Prefer the narrow
  command while iterating, then `composer ci:check` at the end.
- `laravel/pao` is installed, so `php artisan test` and `composer types:check` emit
  machine-readable JSON summaries instead of prose. Parse, don't eyeball.
- `.npmrc` sets `ignore-scripts=true` — postinstall hooks do not run.
- Fresh clone needs `touch database/database.sqlite` before migrating
  (`composer setup` does not create it; only `post-create-project-cmd` does).

## Domain model

All fire-tracker tables are created in **one** migration,
`database/migrations/2026_09_29_161315_create_fire_tracker_tables.php`. There are no
per-model migrations to look for.

```
Client ─┬─> Site ─┬─> Asset ──> Inspection ──> Technician
        │         │     ▲           │
        │         └─> Certificate  └──> AssetType (restrictOnDelete)
        └────────────┴──────────────────┘
```

- `assets.asset_type_id` is `restrictOnDelete`; every other FK cascades. An `AssetType`
  in use cannot be deleted.
- `fire_notifications` has `unique(user_id, type, entity_type, entity_id)` — that
  uniqueness is what makes the notification sync idempotent.
- **There is no `sites.index` route.** Sites are `store`/`update`/`destroy` only and
  are managed inline from the clients page.
- The compliance page lives at URL `/compliance` but its route **name** is
  `certificates.index` and its Inertia component is `compliance` — not `certificates`.

## The RecordPage CRUD convention (most important structural fact)

`resources/js/components/record-page.tsx` is a generic, prop-driven CRUD page. Every
tracker list page is a thin ~100–200 line _config_ of it, not bespoke scaffolding:

- `resources/js/pages/{assets,technicians,inspections,compliance,clients}.tsx` supply
  `columns`, `fields`, `defaults`, `routes`, `statusOptions`, `statusKey`.
- Forms are **declarative**: `resources/js/components/record-form.tsx` renders
  `FormField[]`. Reach for `RecordForm` before hand-writing form JSX.
- `resources/js/components/tracker-filters.tsx` owns debounced search + filter GETs and
  always resets `page: 1`. Don't reimplement filtering in a page.
- `defaults` keys **are** the form's field set — `recordValues()` maps only
  `Object.keys(defaults)`. If `defaults` and `fields` disagree, values silently vanish.
- `columns[].render(record, index)` is reused verbatim by the View modal, so a
  `viewContent` prop is how you add detail-only fields.
- `resources/js/pages/clients.tsx` uses `RecordPage` for client rows but hand-rolls the
  nested "Manage sites" sheet with `RecordForm` — the one place that pattern is broken.
- New pages must be registered in the `management` array in
  `resources/js/components/app-sidebar.tsx` to appear in the sidebar.

Adding a resource is therefore: migration + model + factory + request + controller +
a ~150 line page config. Not a new page scaffold.

## Backend conventions

- Every tracker controller does `use FiltersFireTrackerRecords;` and its FormRequests
  implement `authorize(): return $this->user() !== null`.
- `index()` renders `['records' => …, <lookup collections>, 'filters' => …]`, paginates
  by 10 with `->withQueryString()`, and sets a stable `orderBy('id')` tiebreaker.
- **`filters` must exclude `page`** (`$request->safe()->except(['page'])`). There is a
  test asserting `->missing('filters.page')`; the frontend echoes `filters` back into
  every subsequent GET.
- Every `index()` redirects to the last populated page when `currentPage() > lastPage()`,
  preserving filters. There is a test for this after a delete.
- Search must go through `searchPattern()` + `whereSearchLike()`, which escape `%`, `_`
  and `!` with `ESCAPE '!'`. A test asserts wildcards are matched literally — never
  hand-roll a `LIKE`.
- All date inputs are validated `date_format:Y-m-d`; the frontend must send `Y-m-d`.
- `status` is one shared enum, `all|overdue|due_soon|ok|unknown`, defined in
  `TrackerFilterRequest`. Thresholds: overdue `< today`, due_soon `today..+14d`,
  ok `> +14d`, unknown `NULL`. The **14-day window is duplicated** in
  `FiltersFireTrackerRecords::filterServiceStatus()` and in `serviceStatus()` in
  `resources/js/components/status-badge.tsx` — change both together. Compliance reuses
  this same `status` filter against `expiry_date`.
- Every mutation does `Inertia::flash('toast', ['type' => 'success', 'message' => '…'])`
  then `return back()`. `use-flash-toast` bridges it to sonner.
- `app/Http/Middleware/SyncFireNotificationsAfterWrite.php` wraps **all** tracker write
  routes and re-syncs notifications for the acting user after any non-GET response with
  status < 400. `app/Actions/SyncFireNotifications.php` derives them entirely from
  Asset / Certificate / Inspection state — no queue, no scheduler. It upserts, deletes
  stale rows, and prunes read notifications older than 30 days. If you change those
  models or their date columns, update this action.
- Shared props come from `HandleInertiaRequests::share()`: `today`, `counts` (six
  counters), `fireNotifications`. Read dates from the shared `today` prop
  (`asOfDate={today}`) rather than client `new Date()`.

## Frontend conventions

- Tailwind v4, CSS-first tokens in `resources/css/app.css`. Semantic tokens only —
  `bg-card`, `text-muted-foreground`, `bg-success`, `text-warning`, `text-brand`,

- `resources/js/components/ui/*` is shadcn; prefer extending existing components over

## Testing

- Pest 5. Everything lives in `tests/Feature` (plus a stub `tests/Unit/ExampleTest`).
- `RefreshDatabase` is applied to the `Feature` suite **only**, in `tests/Pest.php` —
  a test placed in `tests/Unit` gets no database.
- Tests use SQLite `:memory:`; local dev uses the gitignored
  `database/database.sqlite`.
- **Time-dependent tests must pin the clock**, because `AppServiceProvider` sets
  `Date::use(CarbonImmutable::class)`:
  `$this->travelTo(now()->setDate(2026, 9, 30)->startOfDay());`
  Unpinned "today" makes status/due-soon assertions non-deterministic.
- Heavy use of Pest datasets with `(model, resource, field, replacement, page)` tuples
  in `tests/Feature/FireTrackerTest.php` — follow that shape for new CRUD resources.
- Assertions are Inertia-shaped: `AssertableInertia as Assert` with
  `->component('assets')->has('records.data', 1)->where(...)`.
- Factories use `->for($site)`, `->for($type)`, `->count(11)`, and
  `User::factory()->unverified()`. Prefer them over hand-built records.
- Auth gating is explicitly tested (guests → `login`, unverified →
  `verification.notice`); mirror those cases for any new route.
- `DatabaseSeeder` creates two hardcoded users and `FireTrackerDemoSeeder` early-returns
  if `Client::exists() || Asset::exists()` — so seeding is a no-op on a non-empty DB.
  Re-run with `migrate:fresh --seed` to reset.

## Gotchas

- `Date::use(CarbonImmutable::class)` means `today()->addDays(14)` returns a **new**
  instance. Use `copy()` when you need both the original and a shifted date
  (`DashboardController` does this).
- PHPStan level 7 with Larastan: the `FiltersFireTrackerRecords` trait carries
  `@template TModel of Model` generics on `Builder<TModel>`. Preserve those docblocks
  when extending the trait.
- Do not add dependencies or new top-level directories without approval.
